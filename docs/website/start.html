    Software is an endless maze of standards, specifications, packages, frameworks, utilities — all touching fundamental concepts regarding the nature of the world we find ourselves in. This collective endeavour marks a high-point in rational human thought and in being so, serves as a "legoland" for the well-tuned mind that finds joy in discovering and manipulating abstract structures using cold, discrete mechanical processes all without breaking a sweat nor leaving the comfort of one’s home. From web technologies, to database technologies, to AI technologies, and so forth, millions of developers are clickity clacking away — sewing a massive technological quilt. metatron is one such patch that provides a distillation of computing down to a few fundamental patterns that, when used together, transform the complex morass of seemingly orthogonal technologies into a comprehensible and usable set of constructs not easily realized nor written using prior art.

    metatron touches on fundamental concepts in languages, compilers, operating systems, networks, databases, web technologies, and more –– all from the vantage point of that enables one to speak to this world at large, simply and effectively.

    Core Concepts

    metatron is a data-oriented programming environment with its own data-flow language called mtron.

    metatron terminal program

    The simplest way to use metatron is as a terminal program.

    $ bin/metatron -e "1-<[+2,+3]"
[3,4]

    However, such stateless one-off interactions don’t capture the full power of metatron. To use metatron as it was intended to be used is through instances of console::T or desktop::T — the REPL terminal application and/or the desktop application, respectively.

    metatron console

    $ bin/metatron -e "console::[⇒]"

    Core Data Types

    In metatron, everything is an obj (an object). There are 3 categories of objs:

    1. mono: objs not composed of other objs:

      • bytes, bool, int, real, str, and uri.

    2. poly: objs composed of other objs in support of nested structures:

      • rel, lst, and rec.

    3. call: objs that can be evaluated by a lhs obj (left-hand side) and an arg obj (lst or rec) to yield a rhs obj (right-hand side):

      • inst and code.

    \[ \tt lhs \underbrace{\Rightarrow}_* inst(\underbrace{arg_0,arg_1,\ldots,arg_n}_+) \underbrace{\Rightarrow}_= rhs \]

    \[ \tt lhs \underbrace{\Rightarrow}_* code\{{\underbrace{inst_0 \cdot \underbrace{(inst_1 + inst_2)}_+ \cdot \ldots \cdot inst_n}_*}\} \underbrace{\Rightarrow}_= rhs \]

    There is one universal obj that is a mono, a poly, and a call: noobj. noobj is similar to the null value found in many programming languages save that it has an operational semantic aligned with its role as the 0-object (zero) of the algebraic ring formed by the set of all objs along with the two ring operators: * and + (apply/compose and branch/split, respectively). Finally, at the other end of the spectrum, there is an obj which serves as the 1-object (one) called "all" and denoted #.

    Any obj with c of {0} is isomorphic to noobj.

    		 
    mtron> {0}1 + 1  [-- noobj * noobj --]
mtron> [noobj,noobj]>-   [-- noobj + noobj --]
mtron> noobj-<[#]>-      [-- noobj * #     --]
mtron> [noobj, #]>-      [-- noobj + #     --]
==><#>

    Any obj applied to # is that obj. Hence why noobj * # => noobj.

    		 
    mtron> #.-<[#]>-          [-- # * #     --]
==><#>
mtron> [#,#]>-            [-- # + #     --]
==>{2}<#>
mtron> #.-<[noobj]>-      [-- # * noobj --]
mtron> [#,noobj]>-        [-- # + noobj --]
==><#>

    Ring Theory

    Ring theory is the beating heart of metatron. Its axioms and subsequent theorems are carefully woven throughout the design, where rings are coupled with rings through the various layers of computing abstraction. The most prominent uses are found in:

    1. the composition of instructions to form code.

    2. the application of objs to other objs.

    3. the joining of objs to form poly(nomial) structures.

    4. the optimization of machine execution via rewrite equivalences.

    5. the construction of types and their constraints on values.

    There is nothing "difficult" about ring theory. In fact, grade school has already ingrained the most important concepts — namely, how * and + operate on objects (e.g. numbers) individually and in concert with one another (e.g. the foil method). In metatron, its not just numbers that are constrained by these axioms, but more generally, objs and various constructions of objs.

    For a gentle, yet thorough presentation on ring theory and its use in metatron, please review stream ring theory.

    Router and Space

    There are 2 "special" rec structures called router and space. They are special in that while they appear as rec objs, they maintain auxiliary data structures (with little reflection enabling reification) accessible only through a particular api not available to other objs.

    router: the purpose of the router is to handle namespace prefix rewrites for local and remote dispatching of read and write calls to spaces. Every instance of metatron has a single running router.

    space: the purpose of a space is to store objs and manage process execution. It is up to the space implementation to determine how objs will be indexed and persisted. However, within metatron, all spaces are functionally equivalent as dictated by a well-defined read/write contract.

    Installation

    1. Download metatron either as an npm package, a dckr container, or a maven project.

    2. Load metatron using a boot file. To run a headless boot in the background, don’t add any UI objs to your boot file. For now, create the following bootloader as plain text — it will spawn an interactive console::T REPL.

    start.mtron bootloader
    import(/m/web);
memspace::[pattern  =>/usr/#, q     =>[docq::[=>],subq::[=>]]]@/sys/space/usr;
memspace::[pattern  =>g:#,    q     =>[subq::[=>]]]           @/sys/space/graph;
fsspace::[pattern   =>local:#,route =>[local: => <~/>]]       @/sys/space/fs;
httpspace::[pattern =>http://#,
             host    =>http://localhost:8765,
             route   =>[/            =>local:]]@/sys/space/http;
console::[=>]@/usr/ui/console;
==>console::[=>]@/usr/ui/console

    To boot a metatron instance from the terminal using start.boot, execute:

    $ bin/metatron "[boot=>start.mtron,log=>info]"

    Console

    After metatron boots, the cursor should be to the right of a mtron> prompt. This is a console::T. The console takes mtron expressions and creates machines to execute them. A machine can be thought of as an executing process.

    mtron> 1 + 2
==>3
mtron> ab * xyz * mn?i=1&j=2
==>ab/xyz/mn?i=1&j=2
mtron> 1-<[_,+ 2,* 5]>-.sum()
==>9
mtron> {1,2,3}-<|[?>1 => +20, _ => * -1]>>
==>-1
==>22
==>23
mtron> 1873-<[http://localhost:${+10}/mcp]
==>[http://localhost:1883/mcp]
mtron> 10.inst(a=>+2,b=>?int::T){ *a + *b }
==>22
mtron> a=>b=>c=>d=>e=>f
==>a=>(b=>(c=>(d=>(e=>f))))
mtron> a=>b=>c=>d=>e=>f.>>.>>.>>.>>.>>
==>f
mtron> [a=>1,b=>[c=>[5,6,7]]]>>b/c/1
==>6

    Space

    The Nature of Space

    At its core, metatron is the infrastructure of a distributed address space used for reading and writing objs, where an address is a key and an obj is the value (a key/value store). This space is aware of the internal structure of the value and supports uniquely identifying substructures in the value (a column store).

    For metatron, the set of all uniform resource identifiers is the address space as it can reference structures at various nested levels of complexity (a web server). The particular uri scheme used by metatron offers more than just the ability to denote the location of an obj, it can also refer to an obj’s type (a semantic web), an obj’s functional signature (a lambda server), and any pre/post-processing read/write modulators (a rest server).

    Nested poly objs provide an interesting twist in that they maintain an internal NAT-like address scheme for routing requests to the objs contained therein (an ldap server). In this way, polys control not just a point in space, but regions of space (a document store) that can overlap, blurring the line between where one poly ends and another begins (an mqtt broker).

    Finally, the objs embedded in space aren’t just static datum (monos) or diffuse collections (polys), they are also active processes (calls) (a lisp interpreter). Amongst the set of calls, there is an interesting instruction called an auto which has the peculiar behavior of dereferencing itself to its referent upon access which yields colocation semantics amongst physically distributed objs (a graph database).

    And that’s just the beginning…​

    The above description may lead one to conclude that metatron, if functional, is too complex to be of practical value. Note that the features articular above are simply epiphenomena of a more fundamental notion of reference. In metatron, the uri is called a fURI (functional uniform resource identifier) and an extreme example of a contrived, fURI is presented below (overly bloated for the sake of coverage).

    abc://example.com:8777/seg1/+/segN[a,b,c]{*}?dom<=rng&k0=v0&k1=v1
 │           │              │   │     │   │     │         └─────── qprocs (query processors)
 │           │              │   │     │   │     └───────────────── domain/range (signature)
 │           │              │   │     │   └─────────────────────── coefficient (cardinality)
 │           │              │   │     └─────────────────────────── polynomial types (generics)
 │           │              │   └───────────────────────────────── hierachial path (navigation)
 │           │              └───────────────────────────────────── wildcard (branching path)
 │           └──────────────────────────────────────────────────── physical location (authority)
 └──────────────────────────────────────────────────────────────── scheme (means of referent access)
