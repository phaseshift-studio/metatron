    A General Theory of Data Access

    In order to access data, it is necessary to understand the geometry of data. That is, the extension or shape of the data. However, the shape we perceive is only tangentially related to the data itself. For example, three people looking at the same table in a room will see three completely different objects. To the first person, floating high above, pinned to the ceiling, the table appears to be a large rectangle. The second person, whose eyes are level with the table, also sees a rectangle, but one that approaches much more of a line, then a large bulky block. And the last, eye level as well, but 90 degrees shifted around the side sees a line-ish rectangle as well, but one that is much smaller than the previous participant’s description.

    The function and purpose of perspective (more generally, the reason for the existence of agenthood in this reality we find ourselves moored to) is made apparent when one wishes to look at data --- a metaphor appropriate for humans, where the more general act is that of accessing data). While the reader searches for some unbeknownst depth in the previous sentence, a sleight of hands on the author’s part and another sort of table emerges which has our participants expressing nearly identical descriptions to those for when the "table" was in the room.

    mtron programs are composed using computational primitives called instructions (inst). Instructions are organized into libraries called instruction sets (instset) — domains of discourse. Mathematically, every instruction is a function that maps a multiset of objs to a multiset of objs — called streams.

    \[ f\left(\cal{P}\left(\tt{X}\right)\right) \rightarrow \cal{P}\left(\tt{Y}\right) \]

    An instruction maps a left hand side obj (lhs) to a right hand side obj (rhs). One-to-one, many-to-one, one-to-many, many-to-many, etc. mappings are possible as domains and ranges are specified as elements of the power set of all objs. When coefficients are elements of \(\mathbb{Z}\), {1,2,3} \(\in \mathcal{P}(\texttt{obj})\) has type int{3}. Programmatically, what is passed between instructions is a single stream of objs. This formulation guarantees that there is always a rhs obj for every lhs obj regardless of failure (fail::T) or emptiness (obj{0}).

    As a side note, discussed at length elsewhere, the mtron inst ring is the set of objs, closed under \(\cdot\) (apply) and \(+\) (split/merge), both of which are total functions.

    inst uri syntax

    In mtron, instructions are written according to the form:

     tid{c}?rng<=dom(args){ code }@vid
  │  │  │      │ │  │  │    │   │
  │  │  └───┬──┘ └─┬┘  └─┬──┘   │
  │  │      │      │     │      └────⮞ value id: the position of the instruction in code
  │  │      │      │     └───────────⮞ code: instruction body is a tree of instructions (impl)
  │  │      │      └─────────────────⮞ arguments: dynamic parameterizations (args)
  │  │      └────────────────────────⮞ domain/range: the incoming (lhs) and outgoing (rhs) obj types
  │  └───────────────────────────────⮞ coefficient: the magnitude of the instruction upon the rhs
  └──────────────────────────────────⮞ type id: the type of the instruction (opcode)

    The instruction template above represents the typical instruction with rng<=dom and {c} sugar syntax being used. However, note that the dom/rng and coefficient sugars ultimately compile to URI query parameters. When fully parsed to a legal URI, the instruction signature is denoted:

    inst?dom=a&rng=b&c=x,y

    Instruction query parameters are similar in function to method annotations. Query parameters encode metadata which can aid the compiler instruction selection, enable code path compression, facilitate polymorphic dispatch, support lifted monadic processing, maintain runtime profiling statistics, and more.

    obj propagation mechanics

    It is important to understand the mechanics of instruction evaluation. Every instruction follows the same pattern. When a lhs obj is applied to an inst obj, the first thing that happens is the arguments of the inst are resolved. This is perhaps best described with an example.

    mtron> 1.plus(2)     ​1​
==>3
mtron> 1.plus(id())     ​2​
==>2
mtron> 1.plus(plus(2))     ​3​
==>4
mtron> 1.map(matches(bool::T))     ​4​
==>false
mtron> 1.map(isa(bool::T))     ​5​
mtron> 1.as(bool::T)     ​6​
==>true
mtron> 1.isa(as(bool::T))     ​7​
==>1
    1 1 is applied to 2 and then 1 is added to 2 to yield 3.
    2 1 is applied to the identity function to yield 1 and then 1 is added to 1 to yield 2.
    3 1 is applied to the instruction plus(2) to yield 3 and then 1 is added to 3 to yield 4.
    4 1 is applied to the instruction matches(bool::T) to yield and then emit bool::false.
    5 1 is applied to the instruction isa(bool::T) to yield and then emit noobj (i.e. nothing).
    6 1 is applied to the instruction as() to emit bool::true (0 would emit bool::false).
    7 1 is applied to the instruction as(bool::T) to yield true and then is applied to isa to allow 1 to pass unfiltered (i.e. not nothing).

    The key point is that call objs (inst, code, and noobj) have a domain and range that are context dependent as each incoming obj creates a chain reaction of internal calls to ultimately yield the arg objs that instruction will operate with. Said another way, calls are types that become instances at time of application.

    the unification of function and value

    Constant objs (non-call objs) also have a domain and range. For instance, the verbose representation of int::1 is <1>?int<=#{?}(){1}.

    mtron> |<1>?int<=#{?}(){1}@<1>   [-- 1 --]
==>1
mtron> <1>()                     [-- 2 --]
==>1
mtron> 10.<1>()                  [-- 3 --]
==>1
mtron> 12 + <1>()                [-- 4 --]
==>13
    1 1 as an inst from maybe an obj to an int (| to prevent evaluation).
    2 noobj applied to the 1 inst (the {0} of the domain’s {?}).
    3 10 applied to the 1 inst (the {1} of the domain’s {?}).
    4 12 added to the 1 inst.

    This states that every lhs obj or noobj (#{?}) that is applied to 1, yields a single rhs int; namely 1. In this way, constants are functions (calls) even though they return the same value regardless of input.

    When an instruction is called, the associated arguments have the lhs obj applied and the result of the application is pushed onto the stack — accessible through reference for the entirety of the inst code block. From this architecture, the following inst forms are made available for use.

    positional args
    \[\tt{obj}_\tt{lhs} \cdot f(\color{yellow}{\__0}, \color{yellow}{\__1},\ldots,\color{yellow}{\__n}) \mapsto \tt{obj}_\tt{rhs}\]

Realize that <1> is uri::1, not int::1. *<0> references the first argument of the args lst, *<1> the second argument, and so forth. Note that for single digit numbers, a syntax sugar exists where the uri < > wrapper isn’t required and the position references can be written as *0, *1, etc.

    dom/rng coefficients

    Every inst has a dom and rng encoded in their key/value query parameters. The dom/rng query parameter values are any fURI minus query parameters (ie. recursive ? is not allowed). What is possible is the specification of a type structure, a coefficient, and polymorphic generics.

       /ex/inst/xyz?poly{c1,c2}[p1,p2,..,pn]<=mono{c3}
        ▲        ▲     ▲        ▲         ▲     ▲
        │        │     │        │         │     │
        │       tid  coeff    poly       tid  coeff
        │        └─────┬────────┘         └──┬──┘
     inst tid         rng                   dom

    An inst to create int triples can be written:

    mtron> trpl -> |inst?lst<=int{3}(){>-[,]}
mtron> {1,2,3,4,5,6}.trpl()
==>[1,2,3]
==>[4,5,6]

    The | token is syntactic sugar for the block inst.

    block?A<=#{?}(A::T)

    A blocked instruction prevents the application of the lhs to the inst args and inst code. This ensures the uri trpl is not applied to the inst prior to the uri being bound as the reference (→). Without block, the result of applying trpl to inst would be what trpl is bound to. In this particular instance, trpl would reference a fail obj.

    mtron>  trpl -> inst?lst[int,int,int]<=int{3}(){>-[,]}     ​1​
==>fail::[lhs range does not match inst domain: uri::T => int{3}::T [inst?rng=lst[int,int,int]&dom=int{3}(){merge([,])}]]@/sys/fail/20
mtron> trpl -> |inst?lst[int,int,int]<=int{3}(){>-[,]}     ​2​
mtron> *trpl     ​3​
    1 if the inst specification is not blocked, then trple is the failure.
    2 the inst specification blocked, enabling trple to be bound to the spec.
    3 dereferencing trple yields the inst specification.

    A stricter, more specific expression of trpl tha leverages polymorphic type constructions is as follows:

    mtron> trpl -> |inst?lst[int,int,int]<=int{3}(){>-[,]}
mtron> {1,2,3,4,5,6}.trpl()
==>[1,2,3]
==>[4,5,6]

    The trpl instruction code is composed of a single instruction: >-[,]. This syntactic sugar resolves merge([,]). The instruction signature of merge is A<=#{*}(A::T). This states that merge is a barrier instruction that maps the entire lhs stream of objs (#{*}) to a single A, where A is a generic bound to lst given the resolution of the argument A::T. Thus, this instance of merge yields a single lst whose elements are the three (int{3}) incoming lhs objs.

    A fundamental requirement for general-purpose computing is branching. Branching occurs when a process chooses one of the myriad of paths through a body of code. This path is the process trace and in classical, non-quantum computing this trace is the result of numerous choices made by the process altering its state given its current instruction and data. Common branching idioms include if/else or while/do or switch/case. These structures typically reside outside the referential purview of the executing process and serve as an existential scaffolding that guides the unwitting process through the code and over the data — instruction by instruction and pointer by pointer.

    mtron has no language construct for branching. Instead, branching is realized as an epiphenomena of the evaluation of two instructions: split and merge (enabled through their respective coefficients).

    \[\begin{align*} \tt{split}&\tt{?}A\{*\} \Leftarrow A & \\ \tt{merge}&\tt{?}A\{*\} \Leftarrow A\{*\} & \end{align*}\]

    Individually, split and merge are "proto"-instructions in that, algebraically, they are not a complete computational step in and of themselves, but when combined, the two yield the abelian group of the mtron inst ring — i.e. the addition operator. When split, but not yet merged, the process is in a state akin to a quantum superposition. In fact, when coefficients are complex numbers, then constructive and destructive interference occurs, effectively rendering the mathematics of Schrödinger’s wave function equation, which for the computationally inclined, is perhaps best conceptualized by Feynman’s path integrals.

    \[\begin{align*} \tt{apply}&\tt{?} B\{\tt{*}\}\Leftarrow A \{\tt{*}\} \end{align*}\]

    The additive component of the mtron ring, split/merge (sugar’d -</>-), is distributive over the ring’s multiplicative monoid, apply (sugar’d .). The relationship between split/merge and apply is significant, with mtron coefficients serving as the glue which renders this coupling algebraically sound (closed under the ring operators). A complete analysis of this algebra is discussed elsewhere. For now, when seen in isolation as a commutative group, the following axioms hold.

    \[ \small \begin{aligned} &\tt{sm}(ca,noobj) &=&\; \tt{ca} + \tt{noobj} &=&\; \tt{ca} & (\text{zero identity})\\ &\tt{sm}(ca,cb) &=&\; \tt{ca} + \tt{cb} &=&\; \tt{sm}(cb,ca) & (\text{commutative})\\ &\tt{sm}(ca,{\text{-}ca}) &=&\; \tt{ca} - \tt{ca} &=&\; \tt{noobj} & (\text{inverse})\\ &\tt{sm}(ca,sm(cb,cd)) &=&\; \tt{ca} + (\tt{cb} + \tt{cd}) &=&\; \tt{sm(sm(ca,cb),cd)} & (\text{associative}).\\ \end{aligned} \]

    When a poly is an argument to split, a new poly is constructed as detailed below for both rec

    \[ \small \tt{obj} \cdot \tt{split}(\tt{rec}) \equiv \left[ \begin{aligned} \tt{obj} \cdot& \tt{dom({rec}_{0})} & \Rightarrow &\; \tt{obj} \cdot \tt{rng({rec}_{0})} \\ \tt{obj} \cdot& \tt{dom({rec}_{1})} & \Rightarrow &\; \tt{obj} \cdot \tt{rng({rec}_{1})} \\ \tt{obj} \cdot& \tt{dom({rec}_{2})} & \Rightarrow &\; \tt{obj} \cdot \tt{rng({rec}_{2})} \\ \vdots & & \Rightarrow &\; \vdots \\ \tt{obj} \cdot& \tt{dom({rec}_{n})} & \Rightarrow &\; \tt{obj} \cdot \tt{rng({rec}_{n})} \end{aligned} \right] \]

    and lst

    \[ \small \tt{obj} \cdot \tt{split}(\tt{lst}) \equiv \left[ \begin{aligned} \tt{obj} \cdot & \tt{dom({lst}_{0})} \\ \tt{obj} \cdot & \tt{rng({lst}_{1})} \\ \vdots &\\ \tt{obj} \cdot & \tt{rng({lst}_{n})} \\ \end{aligned} \right]. \]

    These constructions appear at odds with what is required for branching — namely, discrimination. The ability to choose one branch of code over another is entirely absent in the semantics of split. Every relation in a rec argument and every element in lst argument has the lhs obj applied to it — indiscriminately. Selective discrimination is a consequence of the properties of the abelian monoid (commutative/associative) and its zero element (noobj). Given that a rec relation can not have a noobj domain nor range, then selective branching is achieved programmatically through filtering. That is, given rec relations,

    mtron> [a=>1,b=>noobj,noobj=>3]
==>[a=>1]

    then,

    mtron> {1,2}     ​1​

==>2

                    is(gte(2)) => plus(3)]).rshift()     ​2​
==>10
==>5
    1 two int objs in a stream.
    2 each int obj is split (copied) across the branch arguments (the rels of the rec arg).
    3 gte?bool<=int(int::T) is a one-to-one function which sets up a binary switch (the process is in "superposition").
    4 is?int{?}<=int(bool::T) is a one-to-maybe function that filters paths given a binary signal (the process has chosen its path).
    5 merge?int<=int{*} collapses the two stream pathways into a single stream (the process has "collapsed" into a single branch).

    The above written once more using sugar syntax:

    mtron> {1,2}-<[?<2=>+9,?>=2=>+3]
==>[1=>10]
==>[2=>5]
mtron> {1,2}-<[?<2=>+9,?>=2=>+3]>>
==>10
==>5

    • -< split.

    • ?< is less than.

    • ?> is greater than.

    • >- merge.

    Unlike rec, lst can have noobj elements. However, when merged into a single stream, noobj are discarded.

    mtron> {1,2}-<[gte(2),gt(3)]     ​1​
==>[false,false]
==>[true,false]
mtron> {1,2}-<[?>=2,?>3]     ​2​
==>[noobj,noobj]
==>[2,noobj]
mtron> {1,2}-<[?>=2,?>3]>-     ​3​
==>2
    1 Each incoming obj is split across each "branch" (position) of the lst.
    2 a lst can have noobj elements (empty positions).
    3 The lst is merged into a single stream, thus, filtering out noobj branches.

    While gte?bool<=int(int::T) yields a bool, is?int{?}<=int(bool::T) yields the requisite switch behavior in that the lhs obj is either allowed to pass or not depending on the bool argument. Given inst evaluation semantics, the value of the bool::T argument of is is ultimately dependent on the incoming lhs obj, where

    \[\tt{obj} \cdot \tt{gte}(\_ ) \cdot \tt{is}(\_ ) => obj\{?\} \in \{\tt{obj},\tt{noobj}\}.\]

    In this way, the mechanics of inst lhs-resolution, noobj as the 0-element of the obj ring, and it’s dual usage in both * (filter) and + (clone) provide sufficient infrastructure to render branch semantics in mtron.

    Notes

    metatron introduces the concept of notes to the agent toolkit. Notes are a message board written to and read from (potentially many times) by an LLM during the execution of a task — that is, within a single chat iteration. Notes are useful in the following situations:

    1. real-time feedback: if the agent has made a mistake in their thinking, there is no need to wait for the agent’s response to complete nor halt the agent mid-thought. Instead, a note can be pushed on the agent’s note stack and the agent will pop off the note, read it, and adjust itself accordingly.

    2. real-time system message: the agent’s system message is written at the start of chat and remains static for the duration of the interaction. Notes serve as dynamic system messages allowing programmatic alterations in the agent’s behavior within a single interaction.

    Notes are enabled by adding note=>[,] to the agent’s configuration. The eval tool must also be present — the agent uses it to poll and pop notes from the note stack.

    @<openai:gpt-4o>.at(robotron).
 >>=[feature=>[tool => [!*eval],           (1)
     note => [,]]]                         (2)
    1 eval is required — the agent calls it internally to read and consume notes.
    2 [,] initializes an empty note list and activates the note-checking instruction in the agent’s system message.

    While robotron is executing a task, a note can be pushed at any time from any other mtron context:

    @robotron/note >>= +['actually, can you provide the result in euros, not dollars']   (1)
    1 + concatenates to the note lst. Because the list carries an anchored reference (@vid), the mutation is automatically persisted to space.

    Any obj that carries an @vid is anchored to its spatial location. Mutations to such objs are automatically reflected in the space at that address — no explicit re-assignment required.

    method description

    resources/updated

    Sent when the content of a specific subscribed resource changes; the params include the resource uri, and the client should perform a resources/read to get the new data.

    fail monad

    The diagram above illustrates the concept of monadic computing, where when an exception occurs, the obj is immediately "lifted" out of the instruction space (the graph of inst objs composing a code::T) and continues to propagate to the right unaffected by any subsequent instructions until a "flattening" instruction is met — namely catch(). At which point, catch() tags the fail::T caught and bring it back down into the computational flow of the instruction space.

    fail space

    The diagram above demonstrates that uncaught fail::T objs are routed to fail space. When an exception occurs and a fail monad is created, the fail::T obj is immediately written to the subspace identified at boot/fail_pattern. The uri /sys/fail?incr=./+ is the default fail space pattern. There are two reasons for this behavior.

    1. The exception hasn’t been handled and can be resumed at a later time in a coroutine-esque manner. This is possible even after the underlying machine has completed execution of the instruction graph.

    2. The exception stack trace can be clipped to reduce visual clutter, and only when accessed and caught from fail space will the fail’s trace be unrolled and available to introspection.

    Every obj in mtron has a type. A type is either a base type or some constraint on a base type. For instance, int::5 is a value with type int::T (a base type). However, it is also an int::T[?<10] (a refinement of int::T). In this case, the refinement states that a value of this type is any int::T less than 10. A similar, though more consequential example is the set of natural numbers \(\mathbb{N}\) being a subset of the set of integers \(\mathbb{Z}\). That is, \(\mathbb{N} \subset \mathbb{Z}\). The set of natural numbers is defined in mtron by specifying a predicate (or constraint) on the set of integers.

              int::T[?>0]@nat
          │    │ │    │
          │    │ │    └──────────── type vid
          │    │ └───────────────── predicate inst pred?int{?}<=int(int::T)
          │    └─────────────────── type token
          └──────────────────────── refined type tid

    Non-base types will be notated B::T < A::T: " B::T shares the same, though fewer of the values of A::T." When notated B::T == A::T: " B::T has the same values as A::T ". There exists only a nominal difference between A::T and B::T in the latter relation. A::T and B::T can be used interchangeably.

    Binary vs Decimal Units:

    Metatron’s byte units follow the binary (base-2) convention where:

    • 1 kB = 1024 bytes (not 1000)

    • 1 mB = 1024 kB = 1,048,576 bytes (not 1,000,000)

    • 1 gB = 1024 mB = 1,073,741,824 bytes (not 1,000,000,000)

    This is consistent with how computer systems typically measure memory and storage internally.

    poly types

    Poly types are branched structures where each element or entry represents a separate branch. The two primary poly types are:

    • Each element/entry is a separate branch

    • Branches can be processed in parallel

    The poly types are one of the more interesting aspects of metatron. They are used to structure data (serving as collections) and for for flow control (code branching). There are 3 poly types in metatron: rec (record), lst (list), and rel (relation) — the linchpins of metatron.

    data structures

    The obvious application of a poly is as the scaffolding for a data structure. A poly is a collection able to bundle multiple objs together. Via the colocation of two objs within the confines of a poly, two objs are bound. Another way to bind two objs together is via explicit uri referencing. This method is a form of lazy binding in which "colocation" is computed through dereferencing, and as such, dangling pointers are possible. With poly, there can be no "dangling pointers" — either two objs are colocated in the poly or not. However, mtron is lenient on lazy pointers. It is important to realize the ramifications of the fail-free aspect of noobj resolved pointers.

    graceful degradation in the void with noobj

    The intended use of metatron is to connect disparate datasets and processors into a cohesive structure bound by loose structural similarities. From resources on the web, to LLMs on networked GPU, to vertices linked within a graph database, data entropy will come to fragment structural bonds as different stakeholders within the larger data infrastructure independently alter their sphere of "data influence." In uncertain data environments, noobj and it’s manifestation in maybe/maybe_some coefficients {?}/{*} make dangling pointers and type assumptions convenient for the user.

    mtron> 1-<[?>0,?>2,*/usr/${_}]     ​1​

    A graph is a data structure composed of a set of vertices \(V\) connected by a set of edges \(E\), denoted \[ G = (V,E), \] where \(E\) is typically a partial function \(E \subseteq (V \times V)\).

    ┌────────┐                     ┌────────┐
│        │        edge         │        │
│ vertex ├────────────────────►│ vertex │
│        │                     │        │
└────────┘                     └────────┘

    This classic structure has been extended in various ways since its inception in 1736 (by Leonard Euler). Examples include variants where edges are undirected, labeled, can self-loop, can connect more than two vertices, and more. Modern graph database designers approach graphs with a focus on ease of modeling and speed of querying so to compete with contemporary, complementary technologies such as relational, key/value, column, vector, document, etc. They quickly converged on a particular graph data model colloquially known as a property graph. This structure is known more formally as a directed, labeled, attributed, multi-relational binary graph. The property graph extends \(G = (V,E)\) with properties (key/value pairs) associated with vertices and edges. This extension provides users a convenient path for moving between the dynamic state of a system represented using the constructs of modern object-oriented programming and the persisted state of the system stored in a graph database. As such, property graphs are useful when modeling multi-relational environments, where a heterogeneous set of "things" (different types of vertices) relate to one another via a heterogeneous set of "connections" (different types of edges).

    The graphspace of /m/grph uses Apache TinkerPop as it’s underlying storage framework. While useful for the time being, once metatron’s approach to graphs is fully understood, the constraints imposed by Apache TinkerPop will be made salient. When that time arrives, a generalization will be presented demonstrating the depth of modeling, storage, and processing control one can wield with metatron. This fluidity, a naturalness of form, permeates throughout. It is here where the lines previously drawn between data structures/databases begin to blur, and what emerges renders concepts such as multi-modal, prosaic – a relic of the past.

    graph traversal is uri resolution At its core, metatron is a system designed to map a reference to its referent — i.e., to resolve identifiers.

    In metatron, every piece of data has a unique id — and in fact, many unique ids: as an id is a uri which denotes a particular path through space from point A to point B (and many such paths may exist). However, not all potential paths can be solved with a URI. As such, when a URI segment requires more expressivity than what an explicit selection or wildcard pattern can offer, mtron instructions are attached. Thus, one way to think about mtron is that it’s resolving an identifier, where if a certain fragment requires a more in-depth computation, then that fragment defers to executable function — an inst.

    Property Graph Extensions

    mtron’s design makes possible a swathe of natural extensions to both the standard property graph data model and associated traversal and pattern-matching query engines. The following itemization summarizes some of the more consequential realizations.

    1. hierarchical properties: the folder-like structure of uris combined with mtron pattern matching enables hierarchical organization within the property graph model’s flat namespace.

    2. nested properties: mtron supports poly values meaning element property values can be nested (via rec, rel, or lst).

    3. interspace traversals: !* instructions can be encapsulated as vertices and/or property values, enabling inter- and intra-space traversals.

    4. process encodings: graph databases have historically been used for structuring data, where processes are exogenous to the graph (and execute only at query time). mtron’s inst objs make possible the graph encoding of processes, where, for example, vertices can become active objects within the larger application.

    5. sympathetic partitions: an mtron poly is not constrained to a single space nor within a single space. Neither does an operation on the poly imply a particular physical layout of underlying data. In this way, mtron conveniently supports space agnostic retrieval of data across different physical layouts.

The path form decomposes into g:V (collection), 1 (entry), OUT (direction), te:hot (external-space label), a (edge key), and item (field). The instruction form wraps the same decomposition: outE(te:hot/a) encodes direction + label + key, and >>item projects the field. Both route through the graph engine’s readVertexTraversal, where the scheme prefix te: triggers a read from the external memspace. Whether expressed as uri-path segments or instruction calls, the traversal graph ⎡vertex⎦ → ⎡external edge⎦ → ⎡property⎦ is identical — the instructions are simply an alternate notation for the same underlying path resolution.

    metatron Encoded Graphs

    It is possible to encode an arbitrary graph structure (i.e. any extension of \(G=(V,E)\)) in space. There are four aaspects of mtron that make graph encodings natural and universal — applicable in any metatron space, regardless of the underlying storage system.

    • !* (auto_from): ensures that simply accessing a reference yields the reference’s referent. To the user, there is no difference between the graph elements being colocated in the same poly, within the same space, within the same computer, or across the web as a whole.

    • >> (forward): ensures monads move along the underlying data structure in a manner respective of the provided argument.

    • -< (split): ensures that executing monads will split themselves across branching graph paths and branching code paths.

    • >- (merge): ensures that branching graph and code paths will linearize themselves within the execution path of the machine.

    Machines

    • Swarm Machine

    Every mtron expression is evaluated by a machine. There are various types of machines, each optimized for a particular data processing scenario. Every machine is refinement of virtual::T (a virtual thread).

    mtron> *virtual
mtron> *machine

    The consequence of this type dependence is many fold:

    1. pause/resume: every machine can be paused mid-computation, manipulated/serialized, and restarted.

    2. source: every machine has a source thread that spawned its creation. This source can be another machine (in the case of nested expressions) or a thread (the thread of execution).

    3. call stack: the data structure formed by the !* source relations yields a nested call stack that can be walked in a manner aligned with debugging tools.

    4. pure state: the machine’s state, when separated from its thread of execution is a rec of objs. The relations of the machine include its running monads, its barrier monads, and its halted monads. Thus, the full state of the computation is contained within the machine (where !* is considered containment in simulated co-located sense),

    Swarm Machine

    A swarm::T realizes the computation as a "swarm" of independent, autonomous monads moving over the insts of the machine’s code and, as dictated by the code, over the objs in space. The only coordination that exists in swarm::T is at _barrier instructions. A barrier aggregates all monads up to that point, and when no monads are left outside the barrier, the barrier then drains the monads — allowing them to once again independently execute.

    Thread Refinements

    A virtual thread is a lightweight, cooperative concurrency primitive backed by a Java virtual thread. It shares CPU resources with other virtual threads and is suitable for IO-bound work and high-concurrency workloads.

    A core thread is bound to an OS platform thread from the executor’s pool. It is appropriate for CPU-bound work where you want dedicated execution resources.

    Both types share identical semantics — the same keys, the same lifecycle, the same query surface. The difference is purely in the underlying execution substrate.

    Threads are addressable through the /sys/thread uri space. The thread executor exposes two lst objs — run and stop — for live and completed threads.

    BSON (MongoDB’s binary JSON format) has no concept of a type—​for example, chicken::[name=>'trill', age=>7] stored in MongoDB would ordinarily come back as a plain rec::[name=>'trill', age=>7], losing the chicken::T identity. metatron preserves type information transparently on the way in and restores it on the way out.

mtron> *farm:animals/1/name     ​3​

    bson dbref encoding

    metatron serializes auto_from references as native MongoDB DBRef documents. A DBRef is a plain BSON {$ref, $id} object (no custom fields, no proprietary envelope) so collections with references remain fully compatible with external MongoDB tooling.

    intra-space references store a bare collection name in $ref and the document id in $id:

    {
  "_id": "trill",
  "name": "Trill",
  "age": 7,
  "shelter": { "$ref": "barns", "$id": 1 }
}

    inter-space references prefix the $ref field with the target scheme — the colon is the discriminator that tells the serializer to route through metatron’s router rather than the local database:

    {
  "_id": "trill",
  "name": "Trill",
  "age": 7,
  "shelter": { "$ref": "loc:barns", "$id": 1 }
}

    $id can be an ObjectId (24-char hex), a string, or most numeric types — the serializer auto-detects the format and the deserializer recovers the original id value. $db is deliberately left unused so that existing MongoDB drivers interpret cross-space refs as ordinary references to a collection named "loc:barns" (valid under MongoDB naming rules) until metatron traverses them.

    The loc: prefix in $ref is the only place metatron stores cross-space routing information. There is no _mtron_meta table, no side-channel metadata, and no proprietary BSON type. The reference is a standard DBRef — metatron simply reads the $ref field and checks for a colon. If none is found, the space-local pattern is used; if one is found, the reference is routed to the named scheme’s space.

    Relational Database Rewrites

    Regardless of the language, when querying data, the fundamental primitives of the expression ultimately boil down to a collection of aggregate, filter, project, update, etc. type operations. The universality of these operations across programming and query languages ensure that what can be expressed in mtron can also be expressed in SQL and vice versa (almost). Since relational databases are optimized for processing SQL, it’s best to leverage the backend’s SQL-query engine whenever possible. The rewrite insts of /m/tble do just that. In general, all rewrites are instructions of the form:

    \[ \tt rewrite?code\{?\}⇐code(arg_0,arg_1,\ldots,arg_n). \]

    That is, a rewrite inst takes code (lhs), some rewrite-specific parameters (args), and returns code or noobj (code{?}). The lhs code emerges the rhs code. A semantically equivalent form. But then the process continues. Rewrite after rewrite, sculpting the structural embodiment of a process into a leaner, faster, more efficient form until at some point in time, it stops — the code has reached a stable state distribution. Immune to mutation, timeless by definition, it is ready to be fed to a machine that will use it to guide itself through space in search of a solution it was designed to find. Its destiny awaits.

    auto_from and foreign keys

    In a relational database, rows can be linked in one of two ways:

    1. procedural (where): a runtime process returns implicit relationships.

    2. structural (foreign key): a lookup returns explicit relationships.

    A foreign key in a table cell denotes a reference to a cell in another table. The foreign key states an explicit relationship between two rows. This is analogous to a graph database’s edges making direct, explicit relationships between vertices ("rows"). A where clause comparing columns across two tables computes adhoc relationships between rows. This is analogous to a graph database’s traversals computing new semantic relationships through adhoc walks.

    Two new tables extend the running example to show both patterns. score holds a plain-string player column whose values happen to match person.name — the link is purely algorithmic, enforced only at query time. award holds a !* pointer directly in a recipient cell — the link is structural and immediately navigable.

    mtron> @/sys/space/lite >>= [table=>[person,score]]     ​1​

==>[player=>'marko',points=>42]
mtron> lite:score/2 -> [player=>'grant', points=>99]     ​3​
==>[player=>'grant',points=>99]
mtron> *lite:score/+.=?=[player=>'marko']     ​4​
==>[id=>1,_tid=>'/m/rec',player=>'marko',points=>42]@lite:/sys/space/lite/score/1
mtron> */sys/space/lite.sql("SELECT p.name,p.age,s.points FROM person p JOIN score s ON p.name=s.player")     ​5​
==>[name=>'marko',age=>29,points=>42]
==>[name=>'grant',age=>25,points=>99]
    1 patch the live table config to tell the space about the new score table — on first write the table is created from the record’s field types.
    2 score.player is a plain str — no FK declaration; the correspondence to person.name is purely by shared value.
    3 second score row.
    4 find all scores for 'marko' — =?= (where) rewrites to SELECT * FROM score WHERE player = 'marko'; the join is computed on demand.
    5 the p.name = s.player join expressed in native SQL; both paths return the same result, the first stays in mtron.

    An auto_from (!*) pointer embedded in a row cell is metatron’s structural foreign key. Unlike a matching column value, the pointer encodes the full address of the linked row directly in the data. auto_from is lazy — the cell stores the unresolved pointer until a path traversal forces it.

    mtron> @/sys/space/lite >>= [table=>[person,score,award]];     ​1​

    2 recipient stores a !*lite:person/1 pointer — the FK is part of the row value, not a schema constraint.
    3 second award row linking to lite:person/2.
    4 reading all awards — each recipient cell renders as an unresolved !*lite:person/N pointer.
    5 traversing the FK: the path segment recipient forces auto_from to read lite:person/1 and return the full person row.

    The award => person examples above are intra-space references — both tables live under the same lite: pattern.     foreign key internals

    A tblespace has two storage layers for foreign key pointers. The cell value itself is a plain INTEGER column — no REFERENCES clause, no proprietary SQL type. Routing metadata lives in a single companion table.

    intra- vs. inter-space discrimination

    On write, the cell uri is tested against the space’s pattern:

    ref_uri.matches(*space>>pattern)  [-- true → intra-space, store bare table name in _mtron_meta --]
                                  [-- false → inter-space, store scheme:segment in _mtron_meta --]

    • lite:person/1.matches(lite:#") returns true (same scheme, pattern # matches all).

    • area:V/1.matches(lite:#) returns false (scheme mismatch: area vs lite).

    On read, the ref_table value is checked for a colon:

    *ref_table.has(':') [-- true → inter-space, parse as full uri and extend with foreign key id --]
                    [-- false → intra-space, reconstruct from space pattern --]

    • an intra-space ref_table ?= person is combined with the space pattern to produce lite:person/1.

    • an inter-space ref_table ?= area:V is parsed as g:V/1 — the area: scheme routes through the metatron router.

    sql footprint

    The foreign key column is a bare INTEGER (or TEXT for string keys). There are no SQL FOREIGN KEY constraints and the _mtron_meta table is the only metatron-specific schema artifact. If the database is queried by external SQL tooling, FK columns appear as ordinary integers and _mtron_meta is a readable lookup table — nothing is opaque or encoded.

    Core Structures

    There are four core structures that are required for metatron to function properly.

    1. /m instset: the core instruction set defining the core types — bool, int, rec, etc. It also includes approximately 200 instructions specifically oriented at the core types.

    2. /m/mach instset: the virtual machine that evaluates mtron code, handles thread management, exposes physical machine resources such as the file system and network, and manages each thread’s /m/space/stack (local variable frames).

    3. /sys/router space: a fundamental component that marshalls read/write requests across spaces both inter- and intra- machine. The router indexes spaces and provides namespace services such as routes and redirects.

    4. /sys space: a /m/space/mem in-memory space necessary for hosting the aforementioned components.
