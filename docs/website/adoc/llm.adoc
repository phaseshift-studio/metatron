Modern AI techniques are heavily leveraged across various aspects of metatron, with popular cloud service providers (e.g. link:https://www.anthropic.com/[Anthropic] and/or link:https://openai.com/[OpenAI]) and local providers (e.g. link:https://ollama.com/[Ollama], link:http://lmstudio.ai/[LMStudio], and/or http://localai.io/[LocalAI]) serving as the compute-intensive inferencing backends.

. **Pair Programmer**: LLMs can connect to a console session, be provided a terminal split screen, and evaluate mtron expressions alongside the user. This is especially useful when developing strategies for interlinking spaces via schema alignment and entity resolution as well as quickly creating domain-specific rewrite rules to optimize mtron compilation (using mtron).
. **Agent Development**: A large portion of an LLM's functional elements are embedded in the URI address space and made accessible to mtron via respective spaces. Such components include:
 - **tools**: every mtron `inst` has an `as()`-mapping to `tool`, where the `docq` q processor of the `inst` provides the name, description, and argument notes necessary for LLM tool selection. While most mtron instructions are low-level and not necessarily "tool-oriented," user-defined custom instructions can be defined and offered as tools/services to llms as needed.
 - **thoughts**: when enabling internal reasoning with a supporting LLM, the stream of thought is published streamed and can be directed to system output, to a memory structure, to another LLM for review, etc.  
 - **sessions**: an LLMs interaction/thought history can be stored and retrieved at a later time to enable long-term memory and context awareness.
 - **skills**: an LLM can be trained on a wide range of skills and domains, allowing them to perform complex tasks and solve domain-specific problems. Skills can be pulled from the Anthropic-specified `.agent` directory that has a corresponding `SKILL.md` file and associated resources. Or, can be created programmatically in metaron.
 - **notes**: pass information to an LLM during a chat iteration without interrupting them. LLMs will periodically check their note stack for any advice/information from the user about their task at hand.
 - **prompts**: specific prompts or instructions can be stored and retrieved to help guide an LLM's response.
 - **response formats**: a mtron `rec` can serve as a schema object instructing the LLM to populate the `rec` with their answer to avoid arbitrary string responses in favor of structured responses.
 - **gguff vector files**: ...
. **MCP Servers**: Developing and deploying MCP servers in mtron as well as interacting with remote MCP servers as a client is straightforward. Such simplicity provides a countless number of ways in which LLMs can interact with the underlying spaces.

=== llm space encoding

An LLM is a `model::T < rec::T` with the following type definition:

[mtron]
----
*/m/llm/model
----

The design makes a distinction between the **LLM** (general-purpose reasoning engine) and its **features** (accessories that can be attached to the LLM). Example features include tools, skills, sessions, thinking, response formats, and other similar enrichme. Features are agnostic to the underlying LLM and can be shared between LLMs making it easy to assemble new LLMs from a library of stored features. In `.metatron`, there exists an `agent.mtron` file that provides a sample library.

[mtron]
----
*<mtronfs:agent.mtron>           [-- <1> --]
*<mtronfs:agent.mtron/feature>   [-- <2> --]
----
<1> if a file contains mtron source, the mtron source is the obj referred to by the file uri.
<2> the previous callout entails that a file path can be extended beyond the file boundary.

=== llm interactions

The following example demonstrates how to search for an appropriate LLM for a given task, then query it, and finally, have its session of the interaction stored in space for future use (to provide the agent context over longer interactions). This example relies on an agent `SKILL.md` file stored on the local file system. Thus, we need a space.

[mtron]
----
fsspace::[pattern => fs:#,  /
          route   => [fs: => <~/software/metatron/.metatron/>]]@/sys/space/fs
*<fs:skills/mtron/SKILL.md>
----

++++
<!--   skill   => [!*<fs:skills/mtron>.as(skill::T)],     -->
++++

[mtron]
----
[,]@/usr/ai/session                                        [-- <1> --]
*ollama:+.                                                /
 where(>>skill.has(thinking).has(tools)).                 /
 where(>>size.?>gB::1.0.?<gB::5.0).                       /
 order(>>size * -1.0).                                    /
 take(1).                                                 /
 >>=+[feature=>[                                          /
       session  => [agent     => /usr/ai,                 /
                    user      => /usr/marko,              /
                    name      => 'general chat',          /
                    algorithm => [max=>15]],              /
       tool     => [!*eval],                              /
       think    => print(_),                              /
       response => [to=>to(/usr/ai/response)]]].          /
 to(ai)
[HIDDEN] ai/feature/think -> noobj
----
<1> create a `lst` to server as the an ordered sequence of chat interactions. 
<2> stream all the models currently available on the local ollama server.
<3> filter out those models that don't support thinking and tool use.
<4> filter out models too small (for ollama, the cloud models) and models too big.
<5> reverse sort the models by their size.
<6> select the smallest model of those remaining.
<7> attach features/enrichements to the model.
<8> give the model a session structure for extended context.
<9> give the model access to mtron's eval instruction.
<10> have the model print its thoughts to the console terminal
<11> have the model store its responses to the `/usr/ai` space.
<12> write the model to `ai`.

The first part of the stream above was about widdling down the set of available models to those that meet the requirements for this documentation -- namely, a model that is not too big (as building the docs would take too long) and has some useful capabilities for demonstrating model features.

Once a model was selected, then the second phase served to enrich the model with a session structure (embedded in space), some tools to use if need be (embedded in space), a place for its thought (ephemeral to the console's stdout), and a location to place its response (embedded in space).

With the model loaded and equipped, it's possible to communicate with it.

[mtron]
----
@ai.chat("I need you evaluate the mtron expresion `-<[_=>_]>>.>-[,]-<[_,-<[_=>_]>>]>>.>-` with a lhs of `1`. Please don't tell me the result of the evaluation until I ask for it sometime in the near future.")
----

The `size` relation maps to a `gB::T` (gigabytes) while the `where()` clause filtered on `mB::T` (megabytes). The conversion between the different data size units is handled automatically by the type constructors of those data size types. These types are distributed in the `/m/math` instruction set and imported via `import(/m/math)` (or `import(/m/math,math:)` if naming conflicts may emerge).

[mtron]
----
*/m/math.>>type.>>    [-- <1> --]
----
<1> get the types defined in `/m/math` `instset` and then drain that `lst` to a stream to see a more detailed string representation. 

[mtron]
----
gB::500.0.as(mB::T)    [-- <1> --]
gB::500.0.as(kB::T)    [-- <2> --]
tB::1.0.as(mB::T)      [-- <3> --]
----
<1> convert gigabytes to megabytes
<2> convert gigabytes to kilobytes
<3> convert terabytes to megabytes
--

The content and metadata associated with the chat interaction are stored at the specified location, where it is both read (the previous interaction) and written to (the current interaction).

[mtron]
----
@ai.chat("It's been many years since we last talked. For I am a tired, old man. Before I let my last breathe flutter into this world, I must know one last thing. Please tell me, what was the result of the mtron expression I provided you all those years ago?")
*/usr/ai/session/+
----

Or, using structured responses, the unstructured text result can be turned into a mtron obj.

@ai.chat("what was the answer again?", [answer=>?int::T])

=== llm tools, skills, and mcp servers

LLM tools provide the model a way of calling predefined functions as deemed necessary during chat interactions. In metatron, any `inst` can be a tool. Simply place an `!*` reference to the `inst` into the model's "tool box" (`lst`) at `features/tool`. Next, should MCP tools be required, realize that MCP servers expose their tools as `insts` in metatron as well. Thus, adding an `inst` from an `instset` and adding an `inst` from a `http` or `ws` MCP server endpoint, ultimately boils down to pointing the model towards `insts` it can use to solve problems.


metatron is capable of hosting MCP tools (server), using MCP tools (client), or both. The example below spawns an mtron websocket server and then spawns a client to it as well as other mcp servers not local to metatron.

.metatron hosted mcp server
[mtron]
----
wsspace::[host     => <ws://localhost:8555>,                        /
          pattern  => ws://#,                                       /
          q        => [docq::[=>],subq::[=>]],                      /
          route    => [/mtron=> mtron_ws,                           /
                       /mcp  => mcp_mtron_ws]]@/sys/space/web/ws
----


.metatron hosted mcp clients
[mtron]
----
mcp_client::[host =>                                /
 <ws://localhost:8555/mcp>                          /
]@/usr/ai/mcp/mtron                                 [-- <1> --]
mcp_client::[host =>                                /
 <http://127.0.0.1:29170/index-mcp/streamable-http> /
]@/usr/ai/mcp/intellij                              [-- <2> --]
*/usr/ai/mcp/intellij>>tool.dom()                   [-- <3> --]
----


[mtron]
----
*<openai:gpt-4o>.at(robotron).                                   /  
 side([,].at(<local:.agent/robotron/memory>)).                   /  
 >>=+[feature=>[think=>print(_),                                 /  
      tool=>[!*eval],                                             / 
      skill=>[                                                    /  
  !*<local:.agent/skills/mtron>.as(skill::T)],                   / 
     response=>[to=>print(_)],                                   / 
     memory=>[mem=>!@<local:.agent/robotron/memory>,max=>20]]].  / 
 >>=[_=>^*_]                                                       
----
<1> clone the base model to the `robotron` address
<2> as a side-effect, create a blank memory structure and store it on the local file system
<3> print robotron's thoughts to the terminal
<4> give robotron access to the `eval?A\<=#{?}(str::T)` instruction for evaluating mtron expressions
<5> give robotron the `mtron` skill set (`SKILL.md` file in `.agent/skills/mtron` directory)
<6> print roboton's response to the terminal
<7> pass robotron a reference to the memory structure and cap its growth to 15 entries.
<8> re-reference any resolved `!\*` (`auto_from`) references using `^*` (`auto_to`).

[mtron]
----
@robotron.chat('what tools do you have access to?',          /
            [number_of_tools=>int::T,tool_names=>str::T])        
@robotron.chat('what skills do you have?')                        
*robotron>>feature/session                                                 
*robotron>>feature/session/mem/2/attributes/format                        
----
<1> providing a response format `rec` yields a structured response.
<2> without a response format, the agent replies in free, unstructured text.
<3> the chat session records structured responses.

Given that an `mcp_client::T` is an index of `insts`. Nothing prevents their `insts` being used by other processes such
as a human user. And since, metatron is able to map common data formats to `obj`, its possible to take the result of the
mcp tool and post process it to derive further more refined statistics not offered by the tool.

/usr/ai/mcp/intellij/tool/ide_type_hierarchy(className=>'studio.phaseshift.metatron.isa.m.type.Obj'). /

=== agent notes
metatron introduces the concept of _notes_ to the agent toolkit. Notes are a message board written to and read from (potentially many times) by an LLM during the execution of a task -- that is, within a single chat iteration. Notes are useful in the following situations:

 . **real-time feedback**: if the agent has made a mistake in their _thinking_, there is no need to wait for the agent's response to complete nor halt the agent mid-thought. Instead, a note can be pushed on the agent's note stack and the agent will pop off the note, read it, and adjust itself accordingly.
 . **real-time system message**: the agent's system message is written at the start of chat and remains static for the duration of the interaction. Notes serve as dynamic system messages allowing programmatic alterations in the agent's behavior within a single interaction.

Notes are enabled by adding `note\=>[,]` to the agent's configuration. The `eval` tool must also be present — the agent uses it to poll and pop notes from the note stack.

[source,mtron]
----
@<openai:gpt-4o>.at(robotron).
 >>=[feature=>[tool => [!*eval],           <1>
     note => [,]]]                         <2>
----
<1> `eval` is required — the agent calls it internally to read and consume notes.
<2> `[,]` initializes an empty note list and activates the note-checking instruction in the agent's system message.

While `robotron` is executing a task, a note can be pushed at any time from any other mtron context:

[source,mtron]
----
@robotron/note >>= +['actually, can you provide the result in euros, not dollars']   <1>
----
<1> `+` concatenates to the note `lst`. Because the list carries an anchored reference (`@vid`), the mutation is automatically persisted to space.

[.card]
--
[discrete,.center]
==== @vid auto-persistence
Any `obj` that carries an `@vid` is __anchored__ to its spatial location. Mutations to such objs are automatically reflected in the space at that address — no explicit re-assignment required.

The difference between `.to()` and `.at()` is critical here:

[mtron]
----
1.to(a) + 2 + 3    
*a                 
1.at(a) + 2 + 3    
*a                 
----
<1> `.to()` saves a snapshot at `a` but the `@vid` is **not** carried through the chain.
<2> `a` still holds the original snapshot.
<3> `.at()` binds `@vid` to the result, so every subsequent operation in the chain auto-persists.
<4> `a` reflects the final value of the entire chain.

The note list uses `at()` semantics: `[,]@/usr/ai/notes` initialises the list with its `@vid` already bound, so `@/usr/ai/notes + ['note']` persists automatically without re-assignment.
--

The agent receives the following standing instruction embedded in its system message at `chat()` time:

[.card]
--
[discrete,.center]
==== note-checking protocol
Always check for notes using the `eval` tool before, during, and after your task: +
`*<robotron/note>.remove(0)` +
`noobj` means _no note right now_ — check again later. +
Notes are of **crucial importance** and must be acted on immediately.
--

Notes form a **FIFO queue** — `remove(0)` pops the oldest note, leaving newer ones untouched for subsequent polls. An agent working through a long multi-step task will naturally poll multiple times, consuming notes one at a time as they arrive.

==== mcp server->client notifications in mtron

Typically, a client will request services from an MCP server -- tool listing, tool evaluations, etc. It's important to note that the https://modelcontextprotocol.io/docs/learn/architecture#notifications[MCP specification] has a little known feature that allows the server to initiate communication with the client. This feature is called **notifications** and it can be implemented in pure mtron.

[mtron]
----
<ws://localhost:8555/mcp/+/notifications/#?subq> -> sub::[                /           
 on_recv => inst?#<=lst(message=>?lst::T){                                /
  -<json::[                                                               /
   jsonrpc => '2.0',                                                      /
   method  => >>0 - <ws://localhost:8555/mcp/${*message>>0>>1}${/}>,      /         
   params  => *message>>1](payload=>_){                                   /     
    *<ws://localhost:8555/mcp/${*message>>0>>1}>>>send.apply(*payload)}}]
----
<1> Add the `subq` query processor to the websocket space. This extends the space with pub/sub sematics.

[source,mtron,role="center-code"]
---- 
                     wsspace::[=>]@/sys/space/web/ws
  anywhere            ┌──────────────────────────┐                mcp client
┌─────────┐  write    │ ?subq:            ws://# │  send()      ┌────────────┐
│ payload ├──────────►│ +/notifications/#        ├─────────────►│ intellij/  │
└─────────┘           │                          │ JSON-RPC 2.0 │ claude/... │
                      │ on_recv:                 │              └────────────┘    
 /mcp/0/notifications.│..-<json::[jsonrpc=>...]  │     
                      │    *srv>>>send(*payload) │
                      └──────────────────────────┘
----

The MCP notifications specification notes the following method specs:

[cols=".^2a,.^6",separator=🧱,options=header,role="table-bordered small center"]
|===
^🧱 method ^🧱 description
🧱 `resources/updated`      🧱 Sent when the content of a specific subscribed resource changes; the params include the resource uri, and the client should perform a resources/read to get the new data. 
🧱 `resources/list_changed` 🧱 Sent when the list of available resources has changed, prompting the client to refresh its resource list.
🧱 `prompts/list_changed`   🧱 Sent when the list of available prompt templates has changed.
🧱 `tools/list_changed`     🧱 Sent when the list of available tools has changed (typically when the server declares the listChanged capability).
🧱 `logging/message`        🧱 Sent by the server to provide log output to the client, triggered when the client has configured logging via logging/setLevel.
🧱 `roots/list_changed`     🧱 Sent when the list of filesystem roots accessible to the server has changed.
|===

If an MCP session is spawned at `ws://localhost:8555/mcp/0`, then writing an obj to `ws://localhost:8555/mcp/0/notification/x/y` will automatically be routed to the MCP client in a proper https://www.jsonrpc.org/[JSON-RPC 2.0] transport object.

NOTE: A link:../../.claude/skills/mtron/references/mcp-server-notifications.md[mini-SKILL] is available for this pattern — it captures the development session learnings, pitfalls, and mechanics for agents and users working with MCP server→client notifications.

=== agent-based programming language

The LLM, its sessions, tools, skills, thoughts, and response formats are all first-class entities in the metatron. Interacting
with an LLM is equivalent to evaluating an instruction. Moreover, an LLM's response is simply the `rhs` of
the instruction. As such, in mtron, function composition applies to LLM interactions. 
Agent-oriented computations can be defined and executed in a "workflow" type manner.
Conceptually, the LLM's state exists in (side effect/monadic) space, where instructions along the code's execution path 
can access it accordingly and naturally.

[source,mtron]
----
    enriched llm                                                  
   ┌──────────────────────────────────────────────────┐           
   │       session                      thoughts      │           
   │       tools                        skills        │           
   │       response format              notes         │           
   └──────────────────────────────────────────────────┘           
                   .               .               .              
                   .               .               .              
                   .             ┌────┐            .              
                   .          ┌─►│chat├──────────┐ .              
                   .          │  └────┘          │ .               
                   .          │                  ▼ .              
   ┌────┐        ┌────┐       │  ┌────┐         ┌────┐            
---│    ├───────►│chat├───────┼─►│    ├────────►│chat│---        
   └────┘        └────┘       │  └────┘         └────┘            
                              │                  ▲                 
                              │  ┌────┐          │                
                              └─►│    ├──────────┘                
                                 └────┘                           
----

The mtron example below contains two structured response calls to the agent used in the running examples thus far. Note the use of the tools provided to the agent.

[source,mtron]
----
*robotron                                                                         
*robotron.chat('what is 6 + 23?',[answer=>int::T])                                 /
       .where([answer => ?>20])                                                    /  
       .*robotron.chat('what was the last answer you gave me?',[answer=>int::T])   /
       .>>answer                                                                   /
       .-<|[?>23 => print('a big answer'),                                         /
               _ => print('a small answer')].>>.mult(1000)                         
*<local:.agent/robotron/session>                                                   
----

<1> The agent used in the previous examples.
<2> Treat `chat()` like any other instruction within a larger mtron composition.
<3> The llm's chat sessions with requests and responses accessible.
