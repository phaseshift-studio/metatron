[discrete]
== The Boot Loader 

The boot process for metatron loads a few core components and then hands control over to a user-provided boot script. What the user's boot script does determines the state and use of a particular metatron instance.

[discrete]
=== Core Structures

There are four core structures that are required for metatron to function properly.

[cols="6,4a",separator="🧱"]
|===
a🧱
. *`/m` instset*: the core instruction set defining the core types -- `bool`, `int`, `rec`, etc. It also includes approximately 200 instructions specifically oriented at the core types.
. *`/m/mach` instset*: the virtual machine that evaluates mtron code, handles thread management, exposes physical machine resources such as the file system and network, and manages each thread's `/m/space/stack` (local variable frames).
. *`/sys/router` space*: a fundamental component that marshalls read/write requests across spaces both inter- and intra- machine. The router indexes spaces and provides namespace services such as routes and redirects.
. *`/sys` space*: a `/m/space/mem` in-memory space necessary for hosting the aforementioned components.

[mtron]
----
*/sys/+
----

[discrete]
=== Boot Structures

The boot process maintains provides access to some information that can be useful during the boot process. Note that `boot/` exists under the purview of `/m/space/stack` (patterned `<+/#>`). 

1. The system arguments (`argv`) are stored in `boot/args`.
2. The boot loader file reference is stored at `boot/file`.
3. Other "workspace" related data may also find its way into `boot/+`.

[mtron]
----
*boot/
----

The environmental variables of the underlying operating system are available at `/sys/env/+/`.

[mtron]
----
*/sys/env/+/.take(10)
----

[discrete]
=== Boot Loader

An mtron file can be provided at startup which is used to configure the user's metatron environment. This typically includes mounting spaces (data access points), importing requisite instruction sets (domains of discourse), configuring q processors (documentation endpoints, etc.), defining custom instructions, and putting the system into a console REPL mode or as a headless server only. An example `boot.mtron` is provided below.
