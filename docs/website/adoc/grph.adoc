A graph is a data structure composed of a set of vertices latexmath:[V] connected by a set of edges latexmath:[E], denoted \[
G = (V,E), \]
where latexmath:[E] is typically a https://en.wikipedia.org/wiki/Partial_function[partial function] latexmath:[E \subseteq (V \times V)].

++++
<div style="justify-self:center; width:80%;">
++++

[source,mtron]
----
┌────────┐                     ┌────────┐       
│        │        edge         │        │       
│ vertex ├────────────────────►│ vertex │       
│        │                     │        │       
└────────┘                     └────────┘       
----

++++
</div>
++++

This classic structure has been extended in various ways since its inception in 1736 (by https://en.wikipedia.org/wiki/Leonhard_Euler[Leonard Euler]).
Examples include variants where edges are undirected, labeled, can self-loop, can connect more than two vertices, and more.
Modern graph database designers approach graphs with a focus on ease of modeling and speed of querying so to compete with contemporary, complementary technologies such as relational, key/value, column, vector, document, etc.
They quickly converged on a particular graph data model colloquially known as a *property graph*.
This structure is known more formally as a _directed, labeled, attributed, multi-relational binary graph_.
The property graph extends latexmath:[G = (V,E)] with properties (key/value pairs) associated with vertices and edges.
This extension provides users a convenient path for moving between the dynamic state of a system represented using the constructs of modern object-oriented programming and the persisted state of the system stored in a graph database.
As such, property graphs are useful when modeling multi-relational environments, where a heterogeneous set of "things" (different types of vertices) relate to one another via a heterogeneous set of "connections" (different types of edges).

NOTE: The `graphspace` of `/m/grph` uses http://tinkerpop.apache.org[Apache TinkerPop] as it's underlying storage framework.
While useful for the time being, once metatron's approach to graphs is fully understood, the constraints imposed by Apache TinkerPop will be made salient.
When that time arrives, a generalization will be presented demonstrating the depth of modeling, storage, and processing control one can wield with metatron.
This fluidity, a naturalness of form, permeates throughout.
It is here where the lines previously drawn between data structures/databases begin to blur, and what emerges renders concepts such as __multi-modal__, prosaic – a relic of the past.

=== Traversing Graph Space

Graph traversals in mtron are expressed using either __instruction-call__ syntax or __uri-path__ syntax.
The uri-path form treats `OUT` and `IN` as path segments that route through the graph engine directly, without requiring `out()`, `in()`, etc. instruction calls.
The same traversals expressed using both forms:

[cols="6a,6a",separator=🧱,role="table-bordered small center"]

🧱

[mtron]

*g:V/1                           [-- <1> --]
*g:V/1/OUT                       [-- <2> --]
*g:V/1/OUT/created               [-- <3> --]
*g:V/1/OUT/created/IN            [-- <4> --]
*g:V/1/OUT/knows/IN/name         [-- <5> --]
*g:V/1/OUT/knows/IN/+.count()    [-- <6> --]
*g:E/7/IN/name                   [-- <7> --]

.instruction-call traversals (inst syntax)
[mtron]
----
*g:V/1                          [-- <1> --]
*g:V/1.outE()                   [-- <2> --]
*g:V/1.outE(created)            [-- <3> --]
*g:V/1.out(created)             [-- <4> --]
*g:V/1.out(knows)>>name         [-- <5> --]
*g:V/1.out(knows).count()       [-- <6> --]
*g:E/7.inV()>>name              [-- <7> --]

<1> Vertex `1` with associated properties.
<2> The incident outgoing edges of vertex `1`.
<3> Filter to only edges with label `created`.
<4> Traverse to the incoming vertex of the `created` edge.
<5> The name of the people that vertex `1` knows.
<6> Count of the people that vertex `1` knows.
<7> Edge 7's incoming vertex name.

==== graph traversal is uri resolution At its core, metatron is a system designed __to map a reference to its referent__ -- i.e., to resolve identifiers.
In metatron, every piece of data has a unique id -- and in fact, many unique ids: as an id is a uri which denotes a particular path through space from point **A** to point **B** (and many such paths may exist).
However, not all potential paths can be solved with a URI.
As such, when a URI segment requires more expressivity than what an explicit selection or wildcard pattern can offer, mtron instructions are attached.
Thus, one way to think about mtron is that it's resolving an identifier, where if a certain fragment requires a more in-depth computation, then that fragment defers to executable function -- an `inst`.

[source,mtron]
----
  from()                     where()                             count()
  ┌───┐                   ┌────────────────┐                      ┌────────┐ 
A │ * │g:V/1/OUT/knows/IN │=?=[age=>?>29]>>│ /OUT/created/IN/name │.count()│ B 
  └───┘     │            │└────────────────┘│                    │└────────┘ 
            └─out(knows)─┘                  └─out(created)>>name─┘            
----

With respects to the traversal instructions of `/m/grph`, the instructions `outE()`, `inV()`, `out()`, etc. — inherited from Gremlin — are https://en.wikipedia.org/wiki/Syntactic_sugar[syntactic sugar] that map to standard metatron URI fragments.

=== Property Graph Extensions

mtron's design makes possible a swathe of natural extensions to both the standard property graph data model and associated traversal and pattern-matching query engines.
The following itemization summarizes some of the more consequential realizations.

. *hierarchical properties*: the folder-like structure of uris combined with mtron pattern matching enables hierarchical organization within the property graph model's flat namespace.
. *nested properties*: mtron supports `poly` values meaning element property values can be nested (via `rec`, `rel`, or `lst`).
. *interspace traversals*: `!+*+` instructions can be encapsulated as vertices and/or property values, enabling inter- and intra-space traversals.
. *process encodings*: graph databases have historically been used for structuring data, where processes are exogenous to the graph (and execute only at query time). mtron's `inst` objs make possible the graph encoding of processes, where, for example, vertices can become active objects within the larger application.
. *sympathetic partitions*: an mtron `poly` is not constrained to a single space nor within a single space.
Neither does an operation on the `poly` imply a particular physical layout of underlying data.
In this way, mtron conveniently supports space agnostic retrieval of data across different physical layouts.

[mtron]
----
tblespace::[pattern => acme:#,                                                     /
            host    => <mariadb://localhost:3306/acme?user=mtron&password=mtron>,  /
            route   => [<acme:>=><>],                                              /
            table   => [,],                                                        /
            driver  => <org.mariadb.jdbc.Driver>]@/sys/space/acme;
----

The two data sources have a very particular understanding of how data should be structured and how it should be queried.
The graph database's take on modeling is to see the world as a collection of discrete objects related to one another, where traversals and structural pattern matching are the primary means of understanding the data at large.
The relational database takes the perspective of spreadsheets and set operations.
To unify these two contrasting perspectives, metatron capitalizes on each's most important, distinguishing features.

. *graph features*: explicit references between atomic datum yield an implicit query plan that is the graph itself (it's a pre-joined structure), where traversals serve as result set iterators.

. *relational features*: highly structured, schematically rigorous, where query agnostic endomorphic joins make explicit, references implicit in the data.

[mtron]
----
*g:V/1                                                           [-- <1> --]
*acme:customers/357                                              [-- <2> --]
@g:V/1.addE(consulted,|*acme:customers/357)                      [-- <3> --]
*g:V/1.out(consulted)                                            [-- <4> --]
*g:V/1.out(consulted).matches(vrtx::T)                           [-- <5> --]
----
<1> vertex `v[1]` in a graph database.
<2> row `357` in a relational database.
<3> an edge is created in the graph linking vertex `v[1]` to a reference vertex pointing to row `357`.
<4> traverses the edge to the reference vertex carrying the relational pointer.
<5> a `rrow::T` _is a_ `vrtx::T` according to metatron's structural type system.

The `addE` instruction creates a native TinkerPop edge in the graph that links
vertex `v[1]` to a newly created reference vertex. The reference vertex carries
a `:redirect` property pointing into the relational database via an `!*` auto-from
instruction. The `out(consulted)` instruction traverses the edge to the reference
vertex — the structural type system recognizes the reference vertex as a `vrtx::T`.
The `:redirect` pointer is resolved transparently when the vertex is accessed,
bridging the two data sources.

Some more expressions are provided below that extend what has been constructed thus far.
These expressions highlight the nested structural pattern matching and data manipulation capabilities of mtron.

[mtron]
----
*g:V/1.out(consulted)-<[                                        /
  name    =>"${>>contactFirstName} ${>>contactLastName}",       /
  address =>==[city=>_,country=>_]]
*g:V/1.out(consulted)                                           /
  >>salesRepEmployeeNumber                                      /
  >>reportsTo.-<[                                               /
    name  =>"${>>firstName} ${>>lastName}",                       /
    job   =>-<[title=>>>jobTitle,email=>>>email]]
----

The examples highlight important concepts necessary to understand
in order to be effective at traversing and manipulating complex,
nested structures existing across heterogeneous data sources.

* `-<` (**copy apply**): copy the input `obj` across all slots of the arg `poly`.
* `==` (**match apply**): split the input `poly` to match the slots of the arg `poly`.
* `>>` (**project select**): select a particular component of the input `poly`.
* `${}` (**template select**): process the input `obj` and output a `str` representation of the output `obj`.

.sympathetic partitions
=====

A vertex's edges can span multiple storage backends.
Hot edges (frequently traversed) live in an in-memory space; cold edges (archival) live in a disk-backed space.
The vertex does not know the difference — `*/g/V/1/OUT/+` returns all edges regardless of where they reside.

The following example configures the modern TinkerGraph dataset with two additional edge stores: `hot:` for in-memory edges and `cold:` for disk-backed edges.

.hot and cold edge storage spaces
[mtron]
----
memspace::[pattern  => </te/hot/#>,                          /
           route    => [/te/hot/  => <>]]@/sys/space/hot
tblespace::[pattern => </te/cold/#>,                          /
            route   => [/te/cold/ => <>],                     /
            table   => [,],                                   /
            driver  => <org.sqlite.JDBC>,                     /
            host    => <sqlite:/tmp/cold.db>]@/sys/space/cold
----

Edge data is written into each space keyed by the vertex identifier.

[mtron]
----
/te/hot/1/a  -> [item   => 'laptop', /
                total=>1200.0,      /
                owner  => !*g:V/2]
/te/hot/1/b  -> [item   => 'mouse',total=>25.0]
/te/cold/1/x -> [item   => 'book',total=>15.0, /
                seller => !*g:V/4]
----

Once seeded, the edges are accessible through the same `OUT` traversal used for native graph edges.
The scheme prefix in the label (`te:hot`, `te:cold`) instructs the engine to route the read to the respective space.

|===
🧱

.traversing a distributed edge set (path syntax)
[mtron]
----
*g:V/1/OUT/te:hot/+.count()            [-- <1> --]
*g:V/1/OUT/te:hot/a/item               [-- <2> --]
*g:V/1/OUT/te:hot/a/owner/name         [-- <3> --]
*g:V/1/OUT/te:cold/x/total             [-- <4> --]
*g:V/1/OUT/knows.count()               [-- <5> --]
----

🧱

.traversing a distributed edge set (instruction-call syntax)
[mtron]
----
*g:V/1.outE(te:hot).count()            [-- <1> --]
*g:V/1.outE(te:hot/a)>>item            [-- <2> --]
*g:V/1.outE(te:hot/a)>>owner>>name     [-- <3> --]
*g:V/1.outE(te:cold/x)>>total          [-- <4> --]
*g:V/1.outE(knows).count()             [-- <5> --]
----
|===

<1> Count of hot edges for vertex `1` — returns `2`.
<2> Specific hot edge property value — `"laptop"`.
<3> Passthrough: traverse hot edge → back to graph via `!*` reference → vertex name — `"vadas"`.
<4> Cold edge property value — `15.0`.
<5> Native graph edges coexist with external edges — returns `2`.

The reference `!*g:V/2` in the hot edge's `owner` field creates an `auto_from` pointer back to the graph.
When accessed via `/owner/name`, the pointer resolves to vertex `2` in the graph, and its `name` property returns `"vadas"`.
The traversal path `graph → external edge → graph` is transparent to the user.

The two syntactic forms — `*/g/V/1/OUT/te:hot/a/item` and `*g:V/1.outE(te:hot/a)>>item` — are dual representations of the same underlying identifier resolution.
The __path form__ decomposes into `g:V` (collection), `1` (entry), `OUT` (direction), `te:hot` (external-space label), `a` (edge key), and `item` (field).
The __instruction form__ wraps the same decomposition: `outE(te:hot/a)` encodes direction + label + key, and `>>item` projects the field.
Both route through the graph engine's `readVertexTraversal`, where the scheme prefix `te:` triggers a read from the external `memspace`.
Whether expressed as uri-path segments or instruction calls, the traversal graph `⎡vertex⎦ -> ⎡external edge⎦ -> ⎡property⎦` is identical — the instructions are simply an alternate notation for the same underlying path resolution.

=== metatron Encoded Graphs

It is possible to encode an arbitrary graph structure (i.e. any extension of latexmath:[G=(V,E)]) in space.
There are four aaspects of mtron that make graph encodings natural and universal -- applicable in any metatron space, regardless of the underlying storage system.

* `!*` (**auto_from**): ensures that simply accessing a reference yields the reference's referent.
To the user, there is no difference between the graph elements being colocated in the same `poly`, within the same space, within the same computer, or across the web as a whole.
* `>>` (**forward**): ensures monads move along the underlying data structure in a manner respective of the provided argument.
* `-<` (**split**): ensures that executing monads will split themselves across branching graph paths and branching code paths.
* `>-` (**merge**): ensures that branching graph and code paths will linearize themselves within the execution path of the machine.

.directed single-relational binary graph
=====

A directed single-relational binary graph connects vertices by binary edges (a single tail and a single head vertex), where all edges have the same label/meaning (single-relational).
An example of such a graph is presented in the code and diagram below.

[cols="8a,6a",separator=🧱,role="table-bordered small center"]
|===
🧱
[mtron]
----
v1 -> [!*v2, !*v3, !*v4]
v2 -> [,]
v3 -> [!*v4, !*v5]
v4 -> [,]
v5 -> [,]
v6 -> [!*v4]

v1                 [-- <1> --]
*v1                [-- <2> --]
*v1.>>             
*v1.>>.>>          
----
<1> `v1` denotes the source vertex (0-step traversal).
<2> `*v1` references the adjacent vertices to v1 (1-step traversal).
<3> `*v1>>` traversers the v1 incident edges to the v1 adjanct vertices.
<4> `*v1>>.>>` traveres the those edges emanating from the 3 adjacent vertices to v1.
🧱


[source,mtron]
----

A typical configuration partitions subgraphs by access frequency.
Frequently traversed `knows`-edges reside in `memspace` (sub-millisecond reads).
Rarely queried `purchases`-edges reside in `tblespace` (disk-backed).
The vertex's `OUT` traversal remains a single expression regardless of how many spaces contribute edges.
