== Fail and Catch

The exception handling architecture of metatron leverages a fail monad with some unique features novel to metatron. The fail monad has two states: *propagating* and *caught*.

==== fail monad
The diagram above illustrates the concept of https://en.wikipedia.org/wiki/Monad_(functional_programming)[monadic computing], where when an https://en.wikipedia.org/wiki/Exception_handling[exception] occurs, the obj is immediately "lifted" out of the instruction space (the graph of `inst` objs composing a `code::T`) and continues to propagate to the right unaffected by any subsequent instructions until a "flattening" instruction is met -- namely `catch()`. At which point, `catch()` tags the `fail::T` caught and bring it back down into the computational flow of the instruction space. 
--

[discrete]
=== fail space

The diagram above demonstrates that uncaught `fail::T` objs are routed to _fail space_. When an evaluation halts with a fail monad, the `fail::T` obj is written to the fail stack of the computer that ran the evaluation, `~/processor/computer/<n>/fail/_?incrq`, where `<n>` numbers the evaluation. A `fail::T` raised outside any evaluation is written to the machine's own stack, `~/processor/fail/_?incrq`. There are two reasons for this behavior.

. The exception hasn't been handled and can be resumed at a later time in a coroutine-esque manner. This is possible even after the underlying machine has completed execution of the instruction graph.
. The exception stack trace can be clipped to reduce visual clutter, and only when accessed and caught from fail space will the fail's trace be unrolled and available to introspection.

[mtron]
----
[HIDDEN] @~/processor/computer/+/fail/+.catch(_)
[ERROR] 1.plus(b)                         [-- <1> --]
[ERROR] *~/processor/computer/+/fail/+    [-- <2> --]
@~/processor/computer/+/fail/+.catch(_)   [-- <3> --]
*~/processor/computer/+/fail/+            [-- <4> --]
----

<1> A `fail::T` monad is generated and is not caught.
<2> The uncaught `fail::T` is written to the stack of the computer that ran `1.plus(b)`, `~/processor/computer/<n>/fail`, using the `incrq` query processor.
<3> The uncaught `fail::T` remains uncaught until caught.
<4> A caught `fail::T` is removed from space.

`@~/processor/computer/+/fail/+.catch(_)` is useful `code` for clearing the fail space and releasing memory: `@` reads each `fail::T` where it is filed, so catching it removes it.

[discrete]
=== the cause of failure

Finally, the `cause()` instruction enables recursive stack walking for reflective exception handling.

[mtron]
----
[HIDDEN] @~/processor/computer/+/fail/+.catch(_)
*cause                               [-- <1> --]
1+b.catch(cause())                   [-- <2> --]
throw('bad').catch(cause())          [-- <3> --]
----

<1> The `cause()` instruction has a domain of `fail::T` and range of `fail{?}::T`. The range being potentially a previous underlying `fail::T` to the current/domain `fail::T`.
<2> Once a `fail::T` is caught, it can be applied to `cause()` for introspection.
<3> `throw()` can be used to create a `fail::T` monad.
