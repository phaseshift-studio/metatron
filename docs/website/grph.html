    A graph is a data structure composed of a set of vertices \(V\) connected by a set of edges \(E\), denoted \[ G = (V,E), \] where \(E\) is typically a partial function \(E \subseteq (V \times V)\).

    ┌────────┐                     ┌────────┐
│        │        edge         │        │
│ vertex ├────────────────────►│ vertex │
│        │                     │        │
└────────┘                     └────────┘

    This classic structure has been extended in various ways since its inception in 1736 (by Leonard Euler). Examples include variants where edges are undirected, labeled, can self-loop, can connect more than two vertices, and more. Modern graph database designers approach graphs with a focus on ease of modeling and speed of querying so to compete with contemporary, complementary technologies such as relational, key/value, column, vector, document, etc. They quickly converged on a particular graph data model colloquially known as a property graph. This structure is known more formally as a directed, labeled, attributed, multi-relational binary graph. The property graph extends \(G = (V,E)\) with properties (key/value pairs) associated with vertices and edges. This extension provides users a convenient path for moving between the dynamic state of a system represented using the constructs of modern object-oriented programming and the persisted state of the system stored in a graph database. As such, property graphs are useful when modeling multi-relational environments, where a heterogeneous set of "things" (different types of vertices) relate to one another via a heterogeneous set of "connections" (different types of edges).

    Note
    		 The graphspace of /m/grph uses Apache TinkerPop as it’s underlying storage framework. While useful for the time being, once metatron’s approach to graphs is fully understood, the constraints imposed by Apache TinkerPop will be made salient. When that time arrives, a generalization will be presented demonstrating the depth of modeling, storage, and processing control one can wield with metatron. This fluidity, a naturalness of form, permeates throughout. It is here where the lines previously drawn between data structures/databases begin to blur, and what emerges renders concepts such as multi-modal, prosaic – a relic of the past.

    graph traversal is uri resolution At its core, metatron is a system designed to map a reference to its referent — i.e., to resolve identifiers.

    In metatron, every piece of data has a unique id — and in fact, many unique ids: as an id is a uri which denotes a particular path through space from point A to point B (and many such paths may exist). However, not all potential paths can be solved with a URI. As such, when a URI segment requires more expressivity than what an explicit selection or wildcard pattern can offer, mtron instructions are attached. Thus, one way to think about mtron is that it’s resolving an identifier, where if a certain fragment requires a more in-depth computation, then that fragment defers to executable function — an inst.

      from()                     where()                             count()
  ┌───┐                   ┌────────────────┐                      ┌────────┐
A │ * │g:V/1/OUT/knows/IN │=?=[age=>?>29]>>│ /OUT/created/IN/name │.count()│ B
  └───┘     │            │└────────────────┘│                    │└────────┘
            └─out(knows)─┘                  └─out(created)>>name─┘

    With respects to the traversal instructions of /m/grph, the instructions outE(), inV(), out(), etc. — inherited from Gremlin — are syntactic sugar that map to standard metatron URI fragments.

    Property Graph Extensions

    mtron’s design makes possible a swathe of natural extensions to both the standard property graph data model and associated traversal and pattern-matching query engines. The following itemization summarizes some of the more consequential realizations.

    1. hierarchical properties: the folder-like structure of uris combined with mtron pattern matching enables hierarchical organization within the property graph model’s flat namespace.

    2. nested properties: mtron supports poly values meaning element property values can be nested (via rec, rel, or lst).

    3. interspace traversals: !* instructions can be encapsulated as vertices and/or property values, enabling inter- and intra-space traversals.

    4. process encodings: graph databases have historically been used for structuring data, where processes are exogenous to the graph (and execute only at query time). mtron’s inst objs make possible the graph encoding of processes, where, for example, vertices can become active objects within the larger application.

    5. sympathetic partitions: an mtron poly is not constrained to a single space nor within a single space. Neither does an operation on the poly imply a particular physical layout of underlying data. In this way, mtron conveniently supports space agnostic retrieval of data across different physical layouts.

    tblespace::[pattern => acme:#,                                                     /
            host    => <mariadb://localhost:3306/acme?user=mtron&password=mtron>,  /
            route   => [<acme:>=><>],                                              /
            table   => [,],                                                        /
            driver  => <org.mariadb.jdbc.Driver>]@/sys/space/acme;
    Note

    The two data sources have a very particular understanding of how data should be structured and how it should be queried. The graph database’s take on modeling is to see the world as a collection of discrete objects related to one another, where traversals and structural pattern matching are the primary means of understanding the data at large. The relational database takes the perspective of spreadsheets and set operations. To unify these two contrasting perspectives, metatron capitalizes on each’s most important, distinguishing features.

    1. graph features: explicit references between atomic datum yield an implicit query plan that is the graph itself (it’s a pre-joined structure), where traversals serve as result set iterators.

    2. relational features: highly structured, schematically rigorous, where query agnostic endomorphic joins make explicit, references implicit in the data.

    mtron> *g:V/1     ​1​
==>person::[age=>29,name=>'marko']
mtron> *acme:customers/357     ​2​
mtron> @g:V/1.addE(consulted,|*acme:customers/357)     ​3​
==>consulted::[=>]@g:E/29
mtron> *g:V/1/OUT/consulted/IN     ​4​
mtron> *g:V/1/OUT/consulted/IN.matches(vrtx::T)     ​5​
==>false

    1. vertex v[1] in a graph database.

    2. row 357 in a relational database.

    3. an edge is created in the graph linking vertex v[1] to a reference vertex pointing to row 357.

    4. traverses the edge to the reference vertex carrying the relational pointer.

    5. a rrow::T is a vrtx::T according to metatron’s structural type system.

    The addE instruction creates a native TinkerPop edge in the graph that links vertex v[1] to a newly created reference vertex. The reference vertex carries a :redirect property pointing into the relational database via an !* auto-from instruction. The out(consulted) instruction traverses the edge to the reference vertex — the structural type system recognizes the reference vertex as a vrtx::T. The :redirect pointer is resolved transparently when the vertex is accessed, bridging the two data sources.

    Example 5. sympathetic partitions

    A vertex’s edges can span multiple storage backends. Hot edges (frequently traversed) live in an in-memory space; cold edges (archival) live in a disk-backed space. The vertex does not know the difference — */g/V/1/OUT/+ returns all edges regardless of where they reside.

                   host    => <sqlite:/tmp/cold.db>]@/sys/space/cold

    The reference !*g:V/2 in the hot edge’s owner field creates an auto_from pointer back to the graph. When accessed via /owner/name, the pointer resolves to vertex 2 in the graph, and its name property returns "vadas". The traversal path graph → external edge → graph is transparent to the user.

    The two syntactic forms — */g/V/1/OUT/te:hot/a/item and *g:V/1.outE(te:hot/a)>>item — are dual representations of the same underlying identifier resolution. The path form decomposes into g:V (collection), 1 (entry), OUT (direction), te:hot (external-space label), a (edge key), and item (field). The instruction form wraps the same decomposition: outE(te:hot/a) encodes direction + label + key, and >>item projects the field. Both route through the graph engine’s readVertexTraversal, where the scheme prefix te: triggers a read from the external memspace. Whether expressed as uri-path segments or instruction calls, the traversal graph ⎡vertex⎦ → ⎡external edge⎦ → ⎡property⎦ is identical — the instructions are simply an alternate notation for the same underlying path resolution.

    metatron Encoded Graphs

    It is possible to encode an arbitrary graph structure (i.e. any extension of \(G=(V,E)\)) in space. There are four aaspects of mtron that make graph encodings natural and universal — applicable in any metatron space, regardless of the underlying storage system.

    • !* (auto_from): ensures that simply accessing a reference yields the reference’s referent. To the user, there is no difference between the graph elements being colocated in the same poly, within the same space, within the same computer, or across the web as a whole.

    • >> (forward): ensures monads move along the underlying data structure in a manner respective of the provided argument.

    • -< (split): ensures that executing monads will split themselves across branching graph paths and branching code paths.

    • >- (merge): ensures that branching graph and code paths will linearize themselves within the execution path of the machine.

    Example 6. directed single-relational binary graph

    A directed single-relational binary graph connects vertices by binary edges (a single tail and a single head vertex), where all edges have the same label/meaning (single-relational). An example of such a graph is presented in the code and diagram below.

    mtron> v1 -> [!*v2, !*v3, !*v4]
==>[!*v2,!*v3,!*v4]
mtron> v2 -> [,]
==>[,]
mtron> v3 -> [!*v4, !*v5]
==>[!*v4,!*v5]
mtron> v4 -> [,]
==>[,]
mtron> v5 -> [,]
==>[,]
mtron> v6 -> [!*v4]

mtron> v1     ​1​
==>v1
mtron> *v1     ​2​
==>[!*v2,!*v3,!*v4]
mtron> *v1.>>
==>{2}[,]
==>[!*v4,!*v5]
mtron> *v1.>>.>>

    2. *v1 references the adjacent vertices to v1 (1-step traversal).

    3. *v1>> traversers the v1 incident edges to the v1 adjanct vertices.

    4. *v1>>.>> traveres the those edges emanating from the 3 adjacent vertices to v1.
