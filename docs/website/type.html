    mtron> import(/m/math)
mtron> int::T[?>0]@nat

    Every obj in mtron has a type. A type is either a base type or a refinement on a base type. For instance, int::5 is a value with type int::T (a base type). An example refinement of int::T is the type int::T[?<10]. The refinement type states that a value of this type is any int::T less than 10. A similar, though more consequential example is the set of natural numbers \(\mathbb{N}\) being a subset of the set of integers \(\mathbb{Z}\). That is, \(\mathbb{N} \subset \mathbb{Z}\). The set of natural numbers is defined in mtron as:

    a structural type
              int::T[?>0]@nat
          │    │ │    │
          │    │ │    └──────────── type vid (type being defined)
          │    │ └───────────────── predicate inst pred?int{?}<=int(int::T)
          │    └─────────────────── type token
          └──────────────────────── type tid (type being refined)

    Non-base types will be notated B::T < A::T: " B::T captures a subset of the values captured by A::T." When notated B::T == A::T: " B::T has the same values as A::T ". When two types have the same values but different names (vids), there exists only a nominal difference between A::T and B::T. In such situation, values of A::T and values of B::T are different in that they are being type/classified as being distinct through label (through name). As an example, the type int::T@age is not the same as int::T@zipcode. The structure of a nominal type is specified as:

    a nominal type
              int::T@nat
          │    |  │
          │    │  └──────────────── type vid (type being named)
          │    └─────────────────── type token
          └──────────────────────── type tid (type being renamed)
    Important
    		 The distinction between structural and nominal types depends solely on the existence of a predicate which specifies the structural requirements a value must satisfy to be considered that type. With no constraint on structure, then the implied constraint is on vid, i.e. name.

    Structural Types

    Type Predicates

    A predicate is any inst of the form

    \[ \tt pred?A\{?\} \Leftarrow A()\{ code \}, \]

    such that a lhs value of type A is mapped by code to a rhs value of either type A::T (true) or A{0}::T (false). Hence, A{?} which is sugar for A{0,1}.

    Important
    		 A structural type is any type defined with a predicate.

    Structural Type Hierarchy

    A structural type can be refined with further structural requirements. An example is the concept of age. No human being in modern recorded history has been reported to be over the age of 120 years old. Furthermore, no person has a negative age as at birth, the age is 0. Together, age can be defined as any natural number less than 120 (0 < age < 120).

    Note

For the purpose of these examples, as() is being used to determine whether a value meets the structural requirements of the respective type.     Nominal Types

    As stated in at the beginning of this document, mtron supports both structural and nominal type specifications. A nominal type is any type with no specified predicate. This means that all the base types (e.g. int::T, bool::T, rec::T, etc.) are nominal types. A base type is any type whose tid is equal to its vid. For example, and analogously for the other base types, int::T is defined as:

    mtron> int::T@int

    From mtron’s vantage point at it’s level of abstraction in computing, there is nothing in the definition of a base type that distinguishes it from another base type save the vid/name.

    Important
    		 An int is an int because it is named int.

    Integrating Nominal Types with Structural Types

    With structural types, any rec::T can be a chicken::T as long as it meets the structural requirements of chicken::T. This means, that if a rec::T denotes (in the mind of the engineer) a human (who has a name and age), that human is also a chicken. This can be problematic. For those situations when the value has no other discriminating qualities for a predicate to leverage, then an assigned type label becomes a useful taxonomical criteria.

    mtron> rec::T[?[name=>str::T,age=>age::T]]@being     ​1​
mtron> being::T@human     ​2​
mtron> being::T@chicken     ​3​
mtron> human::[name=>'marko',age=>29].as(chicken::T)     ​4​
==>chicken::[name=>'marko',age=>29]
mtron> chicken::[name=>'snowbutt',age=>7].as(human::T)     ​5​
==>fail::[inst apply failure: chicken::[name=>'snowbutt',age=>7] is not a being::T@human [nominal] (at /m/inst/as@1)]@/sys/fail/114
mtron> [name=>'fuzzy feet',age=>2].as(chicken::T)     ​6​
==>chicken::[name=>'fuzzy feet',age=>2]
mtron> chicken::'punky'     ​7​
==>fail::[parse error at line 1, col 1: chicken::'punky' [string] is not a being::T[?[name=>str::T,age=>nat::T[is(lt(120))]@age]]@chicken
   	while parsing: chicken::'punky']@/sys/fail/115

    1. A being is a rec::T with a name and age.

    2. A person is a type of being.

    3. A chicken is a type of being.

    4. The person named marko is not a chicken.

    5. The chicken name snowbutt is not a person.

    6. A base type value can be nominalized…​

    7. …​as long as the base type of the nominal type matches.

    Structurally speaking, there is nothing that prevents the person named marko from also being a chicken. However, nominally, that is not the case. The person named marko has been nominally relegated to the taxonomical classification of a person. In this way, nominal and structural types co-exist in mtron in order to satisfy two different understandings of type (type by name and type by structure).

    Important
    		 Realize the distinction between structural and nominal types is one of convenience. It is true that there exists structural features of marko that make this person not a chicken (e.g. DNA, weight and size, etc.). However, if the system operating with such types can not make that distinction (perhaps no sensors to do so), then an explicit statement of the fact that marko is not a chicken allows such unrefined systems (literally) to operate effectively using said classification. This is the difference between experiential knowledge (structural) and authoritative knowledge (nominal).
    Note
    		 Type definitions in space are monotonic: once a type is defined with a predicate or constructor, subsequent redefinitions can only add structural constraints, never remove them. If person::T is written as a structural type and later referenced as being::T\@person (a nominal definition with no predicate), the existing predicate is inherited — the type remains structural. This prevents retroactive invalidation of values already constructed and checked against the original type contract. To define a fresh nominal type at a point in space that previously held a structural type, explicitly clear the type from space first (e.g., person -> noobj).

    Type Constructors

              nat::T[?>0][-<|[?<0 => * -1,_ => _]>>]
          │    │ │    │
          │    │ │    └──────────── constructor
          │    │ └───────────────── predicate
          │    └─────────────────── type symbol
          └──────────────────────── tid

    A quick explanation of the type predicate and constructor code is as follows:

    1. predicate [?>0]: is (?) greater than (>) 0.

    2. constructor [-<|[?<0 => ⋅-1,_ => _]>>]: if (-<|) less than (<) 0, then (=>) multiply (*) by -1, else do (=>) nothing (_). Yield the range (>>) of the relation constructed (the specifics of >> will be discussed later).

    Example usage of the defined nat type is presented below.

    1. A natural number with a constructor: the predicate keeps only positive int`s, and the constructor component turns any `int into a positive one (i.e. the absolute value).

    6. -2 fails the natc predicate.

    7. natc::2 * -1 is -2, which fails the natc predicate.

    Common Use Cases:

    • Quota management: Set and compare storage quotas

    Binary vs Decimal Units:

    Metatron’s byte units follow the binary (base-2) convention where:

    • 1 kB = 1024 bytes (not 1000)

    • 1 mB = 1024 kB = 1,048,576 bytes (not 1,000,000)

    • 1 gB = 1024 mB = 1,073,741,824 bytes (not 1,000,000,000)

    This is consistent with how computer systems typically measure memory and storage internally.

    poly types

    Poly types are branched structures where each element or entry represents a separate branch. The two primary poly types are:

    lst (List) - Ordered collection where each element is a branch:

    mtron> [a,b,c]     ​1​
==>[a,b,c]
mtron> [1,2,3]     ​2​
==>[1,2,3]
mtron> [,]     ​3​
==>[,]

    1. List with three branches: a, b, and c

    2. List with three integer branches

    3. Empty list (no branches)

    rec (Record) - Key-value pairs where each entry is a branch:

    mtron> [a=>1,b=>2,c=>3]     ​1​
==>[a=>1,b=>2,c=>3]
mtron> [name=>'Alice',age=>30]     ​2​
==>[name=>'Alice',age=>30]
mtron> [=>]     ​3​
==>[=>]

    1. Record with three branches: a⇒1, b⇒2, and c⇒3

    2. Record representing a person

    3. Empty record (no branches)

    Key Characteristics:

    • Each element/entry is a separate branch

    • .count() returns 1 (the poly object itself)

    • >-.count() merges branches and counts elements/entries

    • Branches can be processed in parallel

    • Support pattern matching and wildcards

    Branching in Action:

    mtron> [1,2,3]     ​1​
==>[1,2,3]
mtron> [1,2,3].count()     ​2​
==>1
mtron> [1,2,3]>-.count()     ​3​
==>3
mtron> [a=>1,b=>2].count()     ​4​
==>1
mtron> [a=>1,b=>2]>-.count()     ​5​
==>2

    1. List with 3 branches

    2. Returns 1 (the list object itself)

    3. Returns 3 (merges branches, counts elements)

    4. Returns 1 (the record object itself)

    5. Returns 2 (merges branches, counts entries)

    instructions

    An inst is an obj of the form:

    \begin{align*} \texttt{inst} = \left(\texttt{uri} \times \left( \texttt{poly} \times \texttt{code} \right) \times \texttt{uri} \right), \end{align*}

    where each component is:

    1. uri: the inst type (e.g. /m/inst/plus).

    2. poly: the inst arguments which can either be a lst or a rec.

    3. code: the code that defines the behavior or function of the inst.

    4. uri: the inst location in space.

    When a tid is specified for an obj, the tid is resolved to an obj denoting the type of that obj.

    Every mtron obj has a type.

    metatron objs are typed. Types are organized into instruction sets that encapsulate the structures and processes necessary to effect domain-specific views of the underlying data space. The type system supports refinement types, optional/maybe types, generic/polymorphic types, recursive/self-referential types, dependent types, type cardinality, and more.
